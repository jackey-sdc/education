# 交互式科学教育辅助系统 - 全局规则

## 1. 目录结构

### 1.1 前端
```
frontend/
├── public/              # 静态资源
├── src/
│   ├── components/      # 可复用组件
│   │   ├── common/      # 通用组件
│   │   └── specific/    # 特定业务组件
│   ├── pages/           # 页面组件
│   ├── services/        # API 服务
│   ├── hooks/           # 自定义 Hooks
│   ├── utils/           # 工具函数
│   ├── constants/       # 常量定义
│   ├── styles/          # 全局样式
│   └── App.js           # 应用入口
├── tests/               # 前端测试
│   ├── unit/            # 单元测试
│   ├── integration/     # 集成测试
│   └── e2e/             # 端到端测试
├── package.json         # 依赖管理
└── vite.config.js       # 构建配置
```

### 1.2 后端
```
backend/
├── app/
│   ├── api/             # API 路由
│   ├── services/        # 业务逻辑
│   ├── models/          # 数据模型
│   ├── schemas/         # 数据校验
│   ├── utils/           # 工具函数
│   └── config/          # 配置文件
├── data/                # 数据库文件
├── tests/               # 后端测试
│   ├── unit/            # 单元测试（方法级）
│   ├── integration/     # 集成测试
│   └── api/             # API 测试（接口级）
├── requirements.txt     # 依赖管理
└── main.py              # 应用入口
```

## 2. 分层设计

### 2.1 前端
- **表现层**：组件和页面，负责UI渲染和用户交互
- **业务逻辑层**：Hooks和服务，处理业务逻辑
- **数据访问层**：API服务，与后端通信
- **工具层**：通用工具函数和常量

### 2.2 后端
- **API层**：处理HTTP请求和响应
- **业务逻辑层**：实现核心业务逻辑
- **数据访问层**：与数据库交互
- **工具层**：通用工具和配置

## 3. 命名规范

### 3.1 前端
- **组件**：PascalCase（如 `UserProfile`）
- **函数**：camelCase（如 `getUserInfo`）
- **变量**：camelCase（如 `userName`）
- **常量**：UPPER_SNAKE_CASE（如 `API_BASE_URL`）
- **文件**：kebab-case（如 `user-profile.js`）

### 3.2 后端
- **类**：PascalCase（如 `UserService`）
- **方法**：snake_case（如 `get_user_info`）
- **变量**：snake_case（如 `user_name`）
- **常量**：UPPER_SNAKE_CASE（如 `API_BASE_URL`）
- **文件**：snake_case（如 `user_service.py`）

## 4. 代码编写要求

### 4.1 前端
- **代码风格**：使用ESLint和Prettier统一代码风格
- **注释**：为复杂逻辑和组件添加JSDoc注释
- **错误处理**：使用try-catch和错误边界处理异常
- **性能优化**：使用React.memo、useMemo、useCallback优化性能
- **测试**：为关键组件和函数编写单元测试

### 4.2 后端
- **代码风格**：使用Black和Flake8统一代码风格
- **注释**：为类和方法添加Docstring注释
- **错误处理**：使用异常处理和自定义异常类
- **性能优化**：使用数据库索引和缓存优化查询
- **测试**：为API和服务编写单元测试

## 5. 版本控制

### 5.1 分支管理
使用Git Flow工作流：
- `main`：稳定版本
- `develop`：开发分支
- `feature/*`：功能分支
- `bugfix/*`：修复分支

### 5.2 提交规范
使用Conventional Commits：
- `feat`：新功能
- `fix`：修复bug
- `docs`：文档更新
- `style`：代码风格修改
- `refactor`：代码重构
- `test`：测试相关
- `chore`：构建或依赖更新

## 6. 文档规范

- **README.md**：项目介绍、安装步骤、使用说明
- **API文档**：使用Swagger或Postman生成API文档
- **组件文档**：为关键组件编写使用说明
- **设计文档**：系统架构、数据库设计、流程设计

## 7. 安全规范

### 7.1 前端
- 使用HTTPS
- 避免XSS攻击，对用户输入进行过滤
- 使用CSRF令牌防止跨站请求伪造
- 敏感信息不存储在本地存储

### 7.2 后端
- 使用JWT进行身份验证
- 密码加密存储
- 输入验证和参数检查
- 防止SQL注入和命令注入
- 合理的权限控制

## 8. 测试规范

### 8.1 测试策略
- **单元测试**：测试单个函数或方法
- **集成测试**：测试模块间的交互
- **API测试**：测试API接口的功能和性能
- **端到端测试**：测试完整的用户流程

### 8.2 测试工具
- **前端**：Jest、React Testing Library、Cypress
- **后端**：pytest、FastAPI TestClient、Postman

### 8.3 测试覆盖率
- 代码覆盖率目标：80%以上
- 关键功能和核心模块：90%以上

### 8.4 测试执行
- 每次代码提交前运行测试
- 每次合并到develop分支前运行完整测试套件
- 每次发布前运行完整测试套件

## 9. 部署规范

### 9.1 本地部署
- 提供启动脚本（Windows和Mac）
- 自动初始化数据库
- 提供环境配置示例

### 9.2 持续集成/持续部署
- 使用GitHub Actions或其他CI/CD工具
- 自动化测试和构建
- 自动化部署到测试环境

## 10. 代码审查规范

### 10.1 审查流程
- 每次代码提交都需要代码审查
- 至少需要1个审查者批准
- 审查者需要检查代码质量、安全性和测试覆盖

### 10.2 审查标准
- 代码符合命名规范和风格指南
- 代码逻辑清晰，易于理解
- 代码有适当的注释
- 代码有足够的测试覆盖
- 代码没有安全漏洞

## 11. 性能规范

### 11.1 前端性能
- 页面加载时间：< 2秒
- 首屏渲染时间：< 1秒
- 动画帧率：60fps
- 代码分割和懒加载

### 11.2 后端性能
- API响应时间：< 500ms
- 数据库查询时间：< 100ms
- 并发处理能力：1000+ 用户同时在线

## 12. 可维护性规范

### 12.1 代码组织
- 模块化设计
- 职责单一原则
- 依赖注入

### 12.2 文档维护
- 及时更新文档
- 文档与代码同步
- 提供示例和使用说明

### 12.3 错误处理
- 统一的错误处理机制
- 详细的错误日志
- 友好的错误提示

## 13. 总结

本全局规则旨在确保项目的代码质量、可维护性和安全性，同时提高开发效率和团队协作。所有团队成员都应该遵守这些规则，确保项目的一致性和可靠性。

在每次代码编写和修改后，都应该进行详细的测试，确保功能正常和代码质量。测试用例应该覆盖接口级和方法级，确保系统的各个部分都能正常工作。
