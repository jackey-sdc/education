> 每轮必须**至少推翻一处**原设计，推翻结论落到代码。

## 一、口算除法：想乘法算除法（#s-oral）

**第一轮｜需求是否清晰**
初稿把「整十数除整十数 → 整十数除几百几十 → 估算」三块平铺成三拍。
→ 推翻：三块其实是**同一个动作**——把 80÷20 想成「20 乘几得 80」。
主线改为「先想乘法 → 再写除法 → 再扩大到几百几十」。

**第二轮｜场景设计是否合理**
迁移拍原本只用 `M.oral2.set(0, 3)` 换第二栏算式，`oral` 主区一动不动，
闸①判「第 6 拍与第 5 拍同画面」。
→ 推翻：迁移必须**同时换主区**。改为 `M.oral.set(24, 3, 1)`（把 240÷30 搬进主区，
并画出"想乘法算除法"的虚线箭头）＋ `M.oral2.set(0, 3)`。
行动：`oralA` 输入框的 `max` 由 12 放宽到 24，容纳 240。

**第三轮｜通俗易懂 + 数学思维**
原来只教「想乘法算除法」这句话，孩子会背不会用。
→ 推翻：要给出**可迁移的判断动作**——「除数是 30，就找 30 的几倍最接近被除数」。
在 `M.oral.set(tens, d, 1)` 里画出 30→60→90 的倍数刻度，让孩子看见"试"的过程，
而不是直接给出答案。

## 二、笔算除法：除到哪一位，商写哪一位（#s-vertical）

**第一轮｜需求是否清晰**
初稿把「列竖式 → 试商 → 乘 → 减 → 落」五步都当成一拍。
→ 推翻：孩子出错不在"会不会算"，在"商写在哪"。
主线压缩为「定位 → 除 → 乘减 → 落 → 验算」，重点放在**商的位置**。

**第二轮｜场景设计是否合理**
原设计只把商的那一位加深底色。
→ 推翻：高亮不算推进。改为在竖式右侧用箭头指向"这一位商对应的被除数片段"，
并在下方写「商 1 表示 1 个 20，不是 1」——必须让标注进 DOM。

**第三轮｜通俗易懂 + 数学思维**
「余数必须比除数小」是规定。
→ 推翻：检验拍要让孩子自己发现**违反规定的后果**——若余数 ≥ 除数，
说明商还能再加 1。把"规定"改写成"可自检的信号"。

---

## 三、试商与调商（#s-trial）

**第一轮｜需求是否清晰**
初稿只讲「四舍五入把除数看作整十数」。
→ 推翻：试商的关键是**商大了调小、商小了调大**，即"错了怎么改"。
主线改为「先粗估 → 试 → 发现偏大/偏小 → 调一次」。

**第二轮｜场景设计是否合理**
原设计只有"试对了"一种情形，孩子看不到调商。
→ 推翻：`M.trial.set(i, s)` 必须能演示**偏大**与**偏小**两种失败，
并在竖式上标出"商偏大，减 1"的红字提示。

**第三轮｜通俗易懂 + 数学思维**
「看作 20 试商」容易被当成唯一方法。
→ 推翻：迁移拍补一句"除数看成几，取决于它离哪个整十数近"，
把方法从口诀变成**依据**（看个位是 1、2、3 还是 7、8、9）。

## 四、商的变化规律（#s-rule）

**第一轮｜需求是否清晰**
初稿把三条规律（除数不变／被除数不变／同时变）并列讲。
→ 推翻：三条规律里只有第三条（同时乘除，商不变）是易错点。
主线改为「一条一条揭示，最后落到商不变」。

**第二轮｜场景设计是否合理**
原设计一次性列出三条结论，孩子只能读不能推。
→ 推翻：`M.rule.set(m, lvl)` 改为**逐级揭示**（lvl 0~3），
每一级只在表格里长出一行，让孩子先看数据再归纳结论。

**第三轮｜通俗易懂 + 数学思维**
「商不变」讲成了"记住它"。
→ 推翻：要讲清它的**用处**——简便计算里把 800÷25 变成 3200÷100。
迁移拍换成一道能口算的题，让孩子感到规律是"省力工具"。

## 五、解决问题：进一法与去尾法（#s-solve）

**第一轮｜需求是否清晰**
初稿把"进一"和"去尾"当两个并列知识点。
→ 推翻：两者是**同一个问题的两种取舍**，取决于"剩下那点还要不要"。
主线改为「算商 → 看余数 → 问一句还要不要 → 定进一还是去尾」。

**第二轮｜场景设计是否合理**
原设计只在文字里说"要进一"，画面不变。
→ 推翻：`M.solve.set(i, phase)` 必须在图上把**最后一组不满的**用橙色虚线圈出来，
并标「只有 N 个」，让"剩下的那点"看得见。

**第三轮｜通俗易懂 + 数学思维**
判断标准靠老师口头说。
→ 推翻：迁移拍给出可复用的自问句——「这点东西**要不要装进车里**？
要，进一；不要，去尾」。把取舍变成孩子自己能问出口的一句话。
